# November 2026 audit

This review started from the published source rather than assuming the existing green test suite established reliability. The baseline passed 169 Python tests and 17 interface checks. New reproductions and a real-model trial still found defects.

## Overall assessment

The useful part of this project is the separation between a persistent task supervisor, disposable model workers, and independent background jobs. Saved objectives, process identities, bounded retries, and current-output checks address a concrete problem for Windows users running local models.

The largest weakness was the gap between file validation and answer correctness. A model could produce a valid Markdown file with wrong numbers and claim it had verified them. The audit also found avoidable completion failures, misleading controls, outdated dependencies, and difficulty finding saved files. These are more important than adding more integrations or making broader marketing claims.

## Findings and changes in 1.0.1

| Finding | Resulting behavior |
| --- | --- |
| An input such as `sales.csv` or `reference.png` could become a required output, unnecessarily blocking a Markdown report or requiring visual review. | Clearly identified input-file clauses are excluded from inferred deliverable requirements. The original brief is preserved. |
| A request for two named outputs could be satisfied by one output of the required extension. | Direct requests such as `Create first.json and second.json` check each filename. |
| A numerical report with guessed totals could pass structural verification. | Numerical data tasks require a recorded successful calculation or verification job covering the current saved output revision. Instructions require code-based calculations and checking job logs. |
| Python commands failed when a model omitted PowerShell quoting around a path with spaces. | `run_python` starts tracked Python jobs with literal paths and argument lists. A native regression checks spaces and shell metacharacters without executing them as shell syntax. |
| Stop could change a completed task's status and end time. | Finished-task metadata is preserved; inappropriate Pause and Stop controls are disabled. |
| A corrupt saved timestamp could break the task list. | Invalid timestamps are skipped rather than breaking all saved-task navigation. |
| Non-string task instructions could be converted into unintended work. | Invalid instruction types are rejected before task creation or steering changes. |
| Model status was hidden with the sidebar on mobile. | A main-workspace connection notice remains visible on narrow screens. |
| Checkpoints appeared as raw JSON; external deliverables could not be opened from their buttons. | Checkpoints have readable labels and an Open task folder button. Only files in the selected task or its reported outputs are authorized for opening. Script/binary outputs show their folder rather than execute. |
| Three pinned packages had advisory findings. | Update Pillow 12.3.0 to 13.0.0, certifi 2026.7.22 to 2026.10.23, and OpenTelemetry API 1.45.0 to 1.45.2. A repeat pip-audit check reported no known vulnerabilities in the pinned requirements. CI repeats the advisory check. |

## Live trial: retain failures as evidence

The numerical task used synthetic CSV input, a real LM Studio backend, and Qwen3.8-27B-UD-Q3_K_XL at a 16,384-token context. It asked for row count, sum of units, and total revenue in a Markdown report. Independent code computed the expected answers: **24 orders, 60 units, and 840 revenue**.

Before the numerical verification rule, the model wrote **24, 96, and 1600**, claimed manual verification, and received completion. The audit's independent arithmetic check caught the error. This is a failed task, even though the model and earlier file gate called it complete.

After the rule and instruction changes, the model used tracked calculation jobs. One unquoted command failed; a corrected command returned **24, 60, and 840**. Saving the report after that calculation required a further verification job; premature completion was rejected. The model then ran that job, inspected its successful result, and completed. Independent checks confirmed the report and unchanged input. The measured task duration was about 202 seconds, including correction attempts. This trial motivated the literal-argument Python tool; it was not a benchmark of that newly added tool.

A separate live task created `first.json` and `second.json`; independent parsing verified both requested contents. That task completed in about 84 seconds. These small trials do not establish a general success rate or performance advantage over other agents.

## Verification scope

- The regression suite now contains **181 Python tests and 20 Node.js interface checks**, including the newly reproduced failure cases.
- A newly created Python environment installed the updated pinned requirements and passed local validation. This is not an installation test on a different physical PC.
- Real browser checks at 1280-pixel and 390-pixel widths covered visible connection errors, completed-task controls, readable progress, and guide layout. No page errors or horizontal overflow were observed.
- Dependency checking used pip-audit 2.10.1. Advisory aliases and duplicate entries are not independent vulnerabilities; the material result is three affected package pins before the changes and no reported findings afterward.
- Source packaging checks the allowlisted inventory, per-file hashes, ZIP CRCs, and reproducibility. Runtime configuration, task histories, models, environments, and private audit fixtures are excluded.
- GitHub Actions runs Windows/Python 3.11, 3.12, and 3.14 plus the dependency audit. Consult [the workflow](https://github.com/orcaonmars/task-continuity-agent/actions/workflows/validate.yml) for each revision's actual result.

## What is still not established

- Execution evidence is stronger than a prose claim, but a successful command can still contain the wrong algorithm or check. Important results need independent review. Natural-language contract inference can misinterpret complex requests.
- The maintainer reports a completed overnight endurance run. That report is separate from this audit's short recorded trials; no new overnight or 50-hour trial was performed here. There is no measured cross-model success rate.
- The application is not a sandbox and uses the signed-in user's permissions. Web and optional integrations can contact external services. Model or tool mistakes remain possible.
- Windows/Python/model setup still requires technical effort. Another physical PC, more model/backend combinations, and optional live Blender integrations need additional validation.
- Output storage has no total quota. Desktop interaction requires an unlocked session; shutdown and power loss end running processes.
- Dependency versions are pinned but not locked to individual distribution hashes. An advisory scan only covers known findings in its current database; it is not a security certification.

## Next priorities

1. Record independent installation attempts and fix the most common setup failures.
2. Publish repeated, comparable task trials with failures, interventions, model/backend settings, and resource use.
3. Expand deterministic user-specified acceptance checks rather than treating model confidence as proof.
4. Broaden compatibility only after the Windows/local-model workflow is consistently useful to actual users.
